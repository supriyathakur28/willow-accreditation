Accreditation Service: Solution Architecture and System Design

Willow Wealth take-home · Supriya Thakur · Design document, version 3 (reviewed; before implementation)

Problem. Admins record and finalise investors' accreditation evidence; the investor app reads the current status. Every change must be auditable through a message broker, and the client view must be built from those events (brief, requirements 1–9).

Shape. One deployable (a modular monolith) on port 9999, built with CQRS and a transactional outbox. Admin commands change the admin write model in MySQL; the state change and its event are written in one transaction. A relay publishes events to Kafka, and consumers build the client read model that GET serves, plus an append-only audit history.

Consistency (Requirement 9b). Rules are checked against the write model, never the eventually consistent projection. A row lock serialises changes to one accreditation, and a pure decide function judges every transition. A unique index on a generated column guarantees at most one PENDING accreditation per user. All of it holds with any number of instances, because MySQL is the only arbiter.

Delivery. Events are delivered at least once; every consumer is idempotent (version guard, unique event_id). A consumer blocks and retries on infrastructure errors and sends only poison events to a dead-letter topic. API retries are safe: an idempotency key stored on the row makes creation exactly-once, and a Redis check rejects a reused key with a different body. Scheduled jobs run on one instance at a time under a MySQL GET_LOCK.

Scale (Requirement 9c). The read side already has its own logical database, connection pool and consumers. Client traffic is absorbed in measured steps: index and pool tuning, horizontal copies, read replicas, a versioned cache, and only then a split into separately scaled services.

Interpretation of requirement 4 and 9b. The brief says the admin endpoints should "leverage the database containing the entity's current state". Read literally, that is the event-built store from requirement 3. Checks against a store that is updated after the request returns cannot be made consistent without making the write wait for the projection. So this design keeps two current-state tables: a write model, updated in the same transaction that records the event and used for every check, and the event-built read model required by requirement 3, used only by the client endpoint. If the literal reading were mandated, the guarantees in section 6 (the answer to 9b) would still need the synchronous table; the projection could then be fed from it rather than replace it.

3. Container view, modules and technology

One MySQL server, two logical databases

The service runs against one MySQL server holding two logical databases (schemas): accreditation_write, the admin write model, and accreditation_read, the client read model. Each has its own datasource, connection pool, database user and Flyway folder. The query module's user has no grant on the write schema, so the boundary is enforced, not conventional; separate pools mean a surge of client reads cannot take the connections admin writes need; and moving the read model to its own server (section 14) changes one JDBC URL. There is no transaction spanning both, by design: the only path between them is the event stream.

Functional core, imperative shell

sealed interface Decision permits Accepted, NoOp, Rejected {}
record Accepted(AccreditationEvent event) implements Decision {}
record NoOp(Accreditation current)       implements Decision {}
record Rejected(RejectionReason reason)  implements Decision {}

// pure: same inputs, same output; no clock, no DB, no exceptions
static Decision decide(Accreditation state, Command cmd, Instant now)
static Accreditation evolve(Accreditation state, AccreditationEvent e)

decide holds the transition rules for 4a, 4b and the expiry rules; evolve applies an accepted event to the write-side state. Business outcomes are values, matched with an exhaustive switch over sealed types, not thrown exceptions. The command service is the thin shell: it loads and locks, calls decide, persists, and maps the decision to a status code. Rule 4c is deliberately not in decide: it spans rows, and the database enforces it (section 6).

The projection does not call evolve. Each event carries a full snapshot of the accreditation, and the projection applies it if its version is newer, so it tolerates gaps and duplicates. Plain Java 21 only (records, sealed interfaces, pattern matching); no functional library.

Technology choices

Java 21, Micronaut 4.10 (Data JDBC, Security JWT), the plain Kafka client with a small consumer loop (capped in-place retry, explicit offsets), MySQL 8.4, Kafka 3.9 (KRaft), Redis 7, Flyway, Testcontainers.

6. Concurrency and invariants (Requirement 9b)

There are two kinds of invariant, and each gets its own mechanism. Both are enforced by the write-model database inside the command transaction, never by the eventually consistent projection, and both hold for any number of service instances because MySQL is the only arbiter.

Topology: "the only arbiter" means one writable primary per record; app pods scale out, replicas only serve reads, and sharding by user_id keeps every user on one primary. Contention: row locks make only requests on the same row wait, for a few milliseconds, so parallel activity across users never waits; a per-user Redis lock would add a round trip to every write without removing any database work.

Interleavings that are handled explicitly

  • Lock, then read. Every command's first statement on the accreditation is the locking read (SELECT … FOR UPDATE); the 404, the If-Match check and decide all use that result. Anything read earlier, such as the expiry job's scan, is used only to find the row by ID, never to decide.
  • Stale admin decision. Admin B reviews X as PENDING and decides to fail it; admin A confirms X first; B's FAILED is now legal against CONFIRMED and would silently revoke A's confirmation. With If-Match: "<version>" on PUT (the version comes from the ETag of the last PUT or from the history endpoint), B gets 412 instead. The header is optional, so the brief's requests work unchanged.
  • Deadlocks. Concurrent inserts that collide on a unique index take shared locks, and three of them can deadlock when the first rolls back (MySQL error 1213). The whole transaction is retried up to twice, then answered with 503. A lock-wait timeout (1205, 3 s) rolls back the whole transaction and returns 503.
  • Isolation level. The write datasource runs at READ COMMITTED. The invariants rest on primary-key locking reads and unique indexes, not on gap locks, and READ COMMITTED avoids gap locks that would otherwise make outbox inserts wait behind cleanup deletes or behind a lookup of a missing ID.

All responses carry X-Request-Id; a caller-supplied value is accepted only if it matches [A-Za-z0-9-]{1,64}, otherwise a new one is generated. It flows to logs, outbox rows and Kafka headers. 9. Data model and identifiers

Identifiers: UUIDv7, stored as BINARY(16)

Accreditation, document and event IDs are UUIDv7, generated by the application: time-ordered, so inserts append to the primary-key index, and not guessable in the API. They are stored as BINARY(16) and exposed as the standard 36-character string.

Column conventions

  • user_id is an opaque, case-sensitive token (the brief's g8NlYJnk…): VARCHAR(64) CHARACTER SET ascii COLLATE ascii_bin in every table, validated at the API as ^[A-Za-z0-9_-]{1,64}$. MySQL's default collation is case-insensitive and would treat abcD and ABCd as one user, leaking one user's accreditations to the other and blocking the wrong user under rule 4c.
  • Times are DATETIME(6) in UTC, always set from the application's injected clock (never ON UPDATE CURRENT_TIMESTAMP, never mixed with the database clock); the JDBC connection and session time zone are fixed to UTC.
  • Enums are VARCHAR with named CHECK constraints rather than MySQL ENUM, so adding a value is a plain migration.

Applying an event to the projection

-- 1. apply the event only if it is newer than what we hold
UPDATE accreditation_views
   SET status = ?, version = ?, updated_at = ?
 WHERE accreditation_id = ? AND version < ?;

-- 2. if no row was updated, insert it
INSERT INTO accreditation_views
  (user_id, accreditation_id, accreditation_type,
   status, version, submitted_at, updated_at)
VALUES (?, ?, ?, ?, ?, ?, ?);
-- duplicate key here: the row exists with the same or a
-- newer version, so the event is ignored

A guarded UPDATE followed, only if it matched nothing, by a plain INSERT. A duplicate event, or one older than the version held, changes nothing; the projection never goes backwards. Each partition has one consumer thread, so two events for the same accreditation are never applied at once; the caught duplicate-key error covers the case anyway.

History inserts catch the duplicate-key error and check which key fired, rather than using INSERT IGNORE, which would also hide other errors.

The document sits in its own table, so status reads never touch the blob. It is decoded and hashed before the transaction begins, so the blob write does not lengthen the time the unique-index lock is held. In production it would go to object storage (section 12), with only the checksum and key kept in the DB. Events never carry the file.

  "performed_by": "admin-7"
}

Named facts. A sealed family: AccreditationSubmitted (version 1, carries document_sha256, no previous status), AccreditationConfirmed, AccreditationFailed and AccreditationExpired. Each reads as an entry in an audit trail, and consumers switch on them exhaustively. The expiry job's events carry performed_by: "system:expiry-job".

Snapshot fields. Every event carries the full current state (user, type, status, version, submitted_at), so a consumer can build or repair its row from any single event. previous_status makes each event a complete from→to change, as requirement 2 asks, without a lookup.

Evolution. Additive changes only within v1; consumers ignore unknown fields. A breaking change means a new topic (v2), written in parallel during migration. Production would enforce this with Avro or Protobuf and a Schema Registry in backward-compatibility mode; here events are versioned JSON, readable with kafka-console-consumer.

Audit record. The topic is the system of record for the audit trail: it is append-only and kept forever. The history table is a queryable projection of it and can be rebuilt from it.

Partition counts. Throughput needs one partition (a few events per second at peak). The counts are sized for consumer parallelism, since a group has at most one active consumer per partition, and so they never need to grow: adding partitions to a keyed topic moves keys and breaks per-key ordering during the change. Two per broker on a three-broker production cluster gives 6; user events are rarer, so 3.

Automatic topic creation is off; a compose init container creates the topics and publishes UserRegistered for the brief's sample user and a few others. Consumer groups: accreditation-projection, accreditation-history, users-write-copy, users-read-copy.

11. Background jobs and threading

JobScheduleWhat it does
Outbox relayevery 500 msDrains: repeats batches of 100 while batches are full; sends a batch asynchronously, flushes, then marks the acknowledged rows in order up to the first failure. Producer timeouts (delivery.timeout.ms 30 s) bound a slow broker. Deletes published rows older than 7 days in primary-key batches of 500.
Expiryhourly (configurable)Computes the cutoff once per run from the injected clock, then walks CONFIRMED rows with updated_at older than 30 days, using the keyset walk in section 9. The scan collects IDs only. Each ID gets its own short transaction: row lock, then eligibility re-checked on the locked row (status is CONFIRMED and updated_at is before the cutoff), then decide, update and outbox event. A row an admin changed after the scan fails the re-check and is skipped, so nothing is ever decided on the scanned values.

One runner per job. Every job method carries @ScheduledJobLock. An interceptor runs SELECT GET_LOCK('job:Class.method', 0) on a dedicated connection: the first pod gets the lock and runs; every other pod gets 0 and skips that run instead of queuing. The lock is held by the connection, so it is released when the job finishes, when the pod dies, or when the connection drops; there is no lease that can expire mid-run. Jobs need MySQL anyway, so this adds no dependency and Redis is never under a job. A MySQL failover drops the lock; a second relay could then overlap briefly, which the consumers absorb (duplicates and reordering are handled by the version guard). If one runner ever becomes too slow, SELECT … FOR UPDATE SKIP LOCKED lets several pods share the work.

12. Security and compliance

Accreditation evidence (tax returns, bank and brokerage statements) is sensitive personal and financial data. Security is fully built but off by default, so the brief's requests run unchanged; SECURITY_ENABLED=true ./run.sh turns it on, and the integration tests run with it on.

ConcernDesign
AuthenticationJWT bearer tokens, signed and checked for expiry. Two kinds: an admin token and a user token (carrying the user_id). In production, admins and users obtain them by logging in with email and password at the authentication service, which is out of scope here; locally, POST /auth/token stands in for those logins.
AuthorisationAdmin endpoints and history require an admin token. GET /user/{userId}/accreditation accepts an admin token, or a user token for that same userId, so a user can never read another user's accreditations.
Audit actorperformed_by and created_by come only from the token subject, never from the body or a header; with security off they are anonymous. The idempotency scope uses the same identity.
Operational endpointsHealth, metrics and Swagger UI on a separate management port, not on 9999.
DocumentsSize-capped before decoding; MIME type from an allow-list (PDF, PNG, JPEG); file_name sanitised (length, path separators, control characters). Documents are never served back by this service. Production: object storage with server-side envelope encryption (KMS) and malware scanning on upload; the database keeps only the key and checksum.
LoggingRequest bodies and document.content are never logged; the HTTP log redacts them. Logs carry IDs and the request ID only.
Retention and erasureAccreditation records fall under regulatory record-keeping obligations that can conflict with GDPR erasure requests. Events carry only user_id and the document checksum, no personal details. Production would encrypt any personal fields per user and destroy the key on erasure (crypto-shredding), so the permanent topic stays append-only; the users topic gets a tombstone.
InfrastructureCompose uses development credentials. Production: secrets from a vault or Kubernetes secrets; TLS everywhere; Kafka and Redis require each service to authenticate, and grant it only the topics, consumer groups and keys it needs; least-privilege database users per schema (the query module has no grant on the write schema).
Input hygieneStrict JSON (unknown fields rejected), validated IDs, a validated or regenerated X-Request-Id so callers cannot inject into logs or headers.

18. Assumptions and scope

Assumptions

  • Allowed transitions: PENDING → CONFIRMED, FAILED or EXPIRED; CONFIRMED → EXPIRED or FAILED (revocation). The brief forbids only updates to FAILED; it does not forbid CONFIRMED → FAILED.
  • PENDING → EXPIRED is allowed ("or the accreditation status has expired").
  • EXPIRED is terminal: once evidence has expired, the user submits fresh evidence as a new accreditation with its own audit trail, rather than an old one being revived.
  • FAILED and EXPIRED cannot be changed (409). Re-sending the current status, in any state, is a no-op returning 200; it emits no event and does not restart the 30-day clock.
  • The 30-day clock runs from updated_at, which equals created_at on insert.
  • A user with a CONFIRMED or EXPIRED accreditation may submit another; only PENDING blocks.
  • user_id is an opaque, case-sensitive token issued by the Users service.
  • POST for an unknown user returns 422; GET for a user with no accreditations returns an empty map.
  • Documents: PDF, PNG or JPEG by declared MIME type, at most 5 MB decoded. The brief's sample content is placeholder text (it decodes to a tsconfig.json fragment), so bytes are not sniffed.
  • Requests with unknown JSON fields are rejected.
  • The client GET is eventually consistent, normally within a second of an admin write.

Designed, not built (README next steps)

  • Gateway rate limiting; keyset pagination; response cache
  • Automatic expiry of PENDING accreditations left unreviewed, so they cannot accumulate and block resubmission
  • Processed-request records written in the same transaction as each change, so any retried request returns exactly its original result
  • Read replicas, the service split and autoscaling (section 14)
  • Object storage with encryption and malware scanning; crypto-shredding
  • Schema Registry; CDC (Debezium) instead of the polling relay
  • OpenTelemetry tracing across Kafka (the request ID is propagated today)
  • Admin listing and search endpoints
